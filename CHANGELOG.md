## [2.7.0] - 2026-08-31

### Added
- **`create-skill`**: meta-skill that probes a capability surface (API, CLI, or MCP server), builds a verified inventory, and writes a tested SKILL.md contract. Seven-phase workflow: gather requirements, build inventory, check existing skills, test/verify, write contract (including an adversarial self-review), register the skill on every surface the repo's contribution contract requires, clean up. Includes `resources/writing-guide.md` (failure-mode checklist, invocation decision, allowed-tools security boundary) and `resources/template.md` (output skeleton). Verified against the `orq` CLI and the orq MCP server on 2026-08-31.

## [2.6.0] - 2026-08-31

### Added
- `orq-evaluator-alignment`: **`{{input.retrievals}}` and `{{input.system_instructions}}` are now fillable**, so a RAG or instruction-following evaluator can be aligned instead of skipping every row. They are real judge input — verified by invoking a live evaluator built on each (2026-08-31): orq substitutes retrievals as newline-joined chunks and system instructions verbatim, and both arrive from the caller's payload, not from a knowledge base. `lib/content` gained the two leaves plus `stringify_retrievals` matching that rendering, and the row shape carries both end to end (`fetch_traces` → `seed` → `judge`). orq emits no span attribute for either, so a trace supplies them only through the template stencil — the same reversal that already recovers `reference` — and a dataset column or `--map` is the reliable source; `SKILL.md` says so at the dataset step. `judged_input_key` appends them only when present, so a row carrying neither keys exactly as before and no in-flight run's `traces_fingerprint` is invalidated.
- `orq-evaluator-alignment`: **`{{output.tools_called}}` (legacy `{{log.tool_calls}}`) is fillable too**, so an agent evaluator that grades tool choice can be aligned. orq does not hand the judge the list the caller passed — it formats it — and this skill re-renders judge prompts locally, so `stringify_tools_called` reproduces the format measured against a live evaluator (2026-08-31): `1. name(args)` / `Status: ✅ Success` / `Response: …`, blank line between calls, `({})` for absent arguments, `Response: N/A` for a call with no result, `No tool calls were made.` for an empty list, and a nameless call dropped before numbering. A string passes through untouched — that is a block orq already rendered, recovered from a judge prompt by the trace stencil. One ceiling, named in the code: `ToolCalled.status` is `'' | in_progress | completed | incomplete | failed`, but the evaluator-invoke API drops it, so `✅ Success` is the only marker any probe could confirm; a non-empty, non-`completed` status prints its own value rather than a guessed `❌`.
- `orq-build-evaluator`: the variable list, the create-step mapping and `resources/judge-prompt-template.md` now name the v4.14+ `{{input.*}}`/`{{output.*}}` variables, including `{{input.system_instructions}}` and `{{output.tools_called}}`, with the legacy `{{log.*}}` names marked as still-resolving rather than current. This skill authors judge prompts, so leaving it on the legacy list meant every *new* evaluator came out in the format the rest of this release migrated away from — and `orq-run-experiment/resources/rag-evaluation.md`, updated in the same work, hands the reader straight to it.

### Added

## [2.5.1] - 2026-08-27

### Fixed
- `evaluatorq`, `orq-compare-agents`: **the skills never said `jobs` takes more than one job**, so every generated script defined one job and any comparison became a loop of `evaluatorq()` calls. Both library examples passed `jobs: [agent_job]`, the only multi-job example lived in `orq-compare-agents/resources/evaluatorq-api.md` (reachable via a link at the bottom of the evaluatorq skill), and `parallelism: 5` appeared in both examples with no explanation of what it gates. In the source (`src/evaluatorq/processings.py`) every job runs against every data point and the jobs for a data point are dispatched together with `asyncio.gather` under a `Semaphore(parallelism)`, while `evaluatorq.py` gates concurrent data points with a second semaphore of the same size; the results table pivots evaluator x job into one comparison. A loop throws all of that away: N unrelated experiments, N tables to diff by eye, no shared sampling, and serialized passes over the dataset. `evaluatorq/SKILL.md` now opens Phase 3 with the rule and a correct/wrong pair before either example, both examples ship two jobs, and the section hands separate-agent comparisons to `orq-compare-agents`, whose Phase 4 now says "a single `evaluatorq()` call" outright.
- `orq-compare-agents`: the documented Python signature had `parallelism: int = 1`; upstream (`src/evaluatorq/evaluatorq.py`) defaults it to `10`. Anyone reading the reference and omitting the argument expected sequential execution and got ten-way concurrency against their provider.

## [2.5.0] - 2026-08-26

### Added
- `orq-evaluator-alignment`: **one list now gates both the step-1 fetch and the step-7 create, and free-form `string` judges are out of scope.** The two gates had drifted apart: `fetch_evaluator` accepted `boolean | categorical | number | numeric | string` while `build_create_body` accepted `boolean | categorical | number`, so a `string` — or a `numeric`, the alias the fetch gate explicitly tolerates and `create_eval` even special-cases for `scale` — passed step 1, paid for the full stability run, the grey-zone loop and the rewrite, and then died at `create_eval --approve`, after `approval.json` had been written. `orq_client.SUPPORTED_OUTPUT_TYPES` and `normalise_output_type` are now the single source of truth both paths resolve through, `numeric` is de-aliased to `number` on the way in so only one spelling reaches the request body, and a test asserts the round trip — every accepted type can actually be created, and every refused type is refused in both places — so the two cannot drift apart again silently. `string` is refused rather than fixed: orq's API accepts the type, but instability over prose is exact-match entropy, which scores nearly every row as maximally unstable and therefore ranks nothing, and gate (b) has no mechanical way to tell a correct answer from one merely worded differently — the alternative being a human reading every pair, which is the manual labelling this skill exists to remove. Removing it takes the whole stop-and-resume-for-a-reader path out of `retest.py` (`string_pairs.json`, `string_pairs_key.json`, `string_verdicts.json`, the blind-shuffle key, the fingerprint check and the sub-run reuse that existed only to keep that resume from livelocking), which simplifies the retest rather than merely shrinking it.
- `orq-evaluator-alignment`: **a dataset whose exchange lives under `messages` no longer maps zero rows** (flow-friction spec §2). `seed.map_datapoint` filled `output` only from `inputs` keys, so a dataset whose `inputs` carried metadata — category, difficulty, ground_truth — while the actual exchange sat in `messages` reported `✓ Added 0 rows; 42 skipped (unmappable)` with `missing ['log.output']` on every one. The output was right there: `log.output` is the assistant's last turn. Production traces never hit this because orq's `gen_ai.input` supplies `output` outright; the dataset path is the one that has to derive, and had no rule to derive with. `lib/content.derive_io_from_messages` is now that rule — last `assistant` turn → `output`, last `user` turn → `query`, read through `message_text` so Responses-API `parts[]` and multimodal turns resolve exactly as the trace scanner resolves them. It lives in `content.py` rather than `seed.py` because that module is the shared vocabulary and the scanner will need the same rule the day it meets a span with messages and no explicit output. `inputs` still wins; derivation is fallback only; `system`/`tool` turns are never the output; and a message with no `role` is still skipped rather than guessed at positionally, so genuinely unmappable data fails exactly as before. Diagnostics are now **per dataset, not per row** — one inventory naming what the judge needs, what the dataset holds, and what each field could map to, in place of N identical skip lines — plus a `--map "log.output=messages.assistant.last"` escape hatch over a deliberately tiny grammar (an unknown source is an error, never a silent skip) recorded in `input_mapping.json`. A pull that maps nothing now stops instead of appending zero rows and reporting success.
- `orq-evaluator-alignment`: **ground truth is used instead of collected and dropped** (flow-friction spec §3). `map_datapoint` correctly routed a dataset's `expected_output` into `reference` — and nothing downstream ever read it, because an evaluator that declares no `{{reference}}` variable never renders it. So the skill kept repeating that it "structurally cannot find cases the judge gets wrong with total confidence" while sitting on the labels that answer exactly that. `reference` now rides through `stability.json`, and `metrics.json` carries a `correctness` block: accuracy, a confusion tally, and — the point — **`by_band`**. Accuracy among the rows the judge was *stable* on is the consistently-wrong blind spot, measured rather than caveated: a judge at 0.0 mean instability and 60% correct on stable rows is the exact failure everything else here is blind to, and it now leads the report. `build_queue` gained a third confuser class, `wrong_vs_reference` — stable and disagreeing with the label, the highest-information rows in a run and previously invisible — appended as its own reason rather than interleaved, so the instability ranking stays a clean single-metric order. The grey-zone payload carries `reference` and `judge_correct` so the conductor can group by *how* the judge is wrong rather than only by what it is unsure about, and the retest may fill unanswered rows from dataset labels, tagged `dataset_reference` in `label_provenance` and never merged into the human-answer count. Guardrails throughout: a label that will not parse into the verdict space is excluded and warned about rather than counted as the judge being wrong; SKILL.md now branches — state the blind spot when there are no labels, state what was actually verified when there are — and requires the user to confirm a dataset label before it drives a rewrite.
- `orq-evaluator-alignment`: **the regression check now covers every re-judged row nobody labelled, and the report says how far it looked.** `_regression_report` was called with `_low_flip_indices(out_dir) & scope` — the ~5 stable spot-check rows the queue holds back — so a rewrite could move behaviour across the rest of the dataset and the retest would still print "0 of 5 previously-stable rows changed". True, and read by everyone as "nothing regressed". `--all_rows` already re-judged everything, but the regression view stayed pinned to those five, so even the expensive option did not widen the answer. `retest_metrics.json` now carries `regression_on_unlabelled_rows` (every re-judged row without a human label — the labelled ones are *supposed* to change, so counting them would report the rewrite working as if it were misfiring) alongside the existing `regression_on_stable_rows`, plus `regression_scope` recording how many of the original datapoints were actually re-judged. A caveat fires whenever that is narrower than the original run, and SKILL.md step 8 now *asks* — "want me to re-run the new judge over all 200 original datapoints and show you what moved? about the same cost as the first run" — rather than leaving `--all_rows` as a flag nobody offers. Worth asking out loud because the answer depends on something the skill cannot see: whether the evaluator is already scoring live traffic.
- `orq-evaluator-alignment`: **the input source is now a question, not a default.** `fetch_evaluator.py` chained straight into a 200-trace scan, which answered "where should the examples come from?" silently and framed the other three sources — an orq dataset, examples the user brings, generated cases — as *recovery options*, reachable only once the scan had come back starved. That reading is backwards for a judge that went live yesterday, fires rarely, or is older than the scan window: those users met an empty scan that looks like a dead end rather than a menu they were always entitled to. `fetch_evaluator` now fetches the judge and stops (`--with_traces` re-enables the chained scan once the user has picked that route), and SKILL.md step 1a asks the question outright with all four routes on it. The trace scan is still led with and still named as the only source that shows what the judge meets in production — a real difference, and the reason to prefer it — but it is presented as the option to beat rather than the one already taken. Sources compose, so "scan production, then top up with generated borderline cases" is now an ordinary answer; because the scan **overwrites** `traces.jsonl` while the other three **append**, it must run first, and it now refuses (rather than silently deleting) when it finds rows from another source, with `--replace` as the deliberate override.
- `orq-evaluator-alignment`: **the scan reports its depth, and offers to go deeper before the run is priced.** The trace scan reads the 200 most recent traces, and it reported only the datapoint count — so "18 examples" read as everything this judge has, when it is 18 out of a 200-trace slice of a longer history. The deeper scan existed but was filed under step 1a, reachable only once the scan had come back *starved* (fewer than 10 usable examples); a judge with 18 went straight on. `fetch_traces` now prints the count next to the window it came from and writes `scan.json`, and the conductor stops there to offer `--trace_limit 2000`. The offer is placed before step 2 deliberately: pulling more traces costs no judge calls, and it rewrites `traces.jsonl`, which is safe now and unsafe once anything is labelled — so this is the last moment the choice is free. It is also *conditional*, on the new `scan_truncated` flag: the deeper scan is offered only when the scan stopped **at** the cap, which is the tell that history remains behind it. A scan that came back under the cap already saw every trace in the window, so a bigger limit would re-scan the same traces and find the same rows; there the note points at `trace_start_date`/`trace_end_date` instead. Offering a remedy that cannot help is how a gate teaches people to click past it.
- `orq-evaluator-alignment`: **`orq_router` is the new default backend** for the recommendation and rewrite stages — any workspace model over the OpenAI-compatible `/v3/router`, using the `ORQ_API_KEY` the skill already requires, defaulting to `deepseek/deepseek-v4-pro`. The rewrite is a text transform, not an agentic task, and the previous default (`claude_subagent`) silently assumed the `claude` CLI was installed *and* logged in. `backend_model` is now optional per backend, so switching `backend` alone is a valid edit instead of quietly handing a Claude model id to the router. Calls are priced from the registry's own per-1K rates rather than reported as zero. Step 7 states the model, notes it must be enabled on the workspace, and offers the two alternatives (another model by `refId`, or the Claude subagent); both scripts preflight with one tiny call and stop with an actionable reason — 403 vs 404 vs 429 are distinguished — rather than failing partway through a paid run.
- `orq-evaluator-alignment`: **the backend's endpoint, model and credential are now an explicit, parameterised surface.** `recommend.py` and `rewrite_eval.py` take `--backend`, `--backend_model` and `--backend_base_url`, each resolving flag → `config.toml` → environment variable → built-in default, so a self-hosted or proxied orq (or an Anthropic-compatible gateway) is a flag rather than a code edit. `--help` prints all three with their fallbacks, `BACKEND_ENV` in `lib/model_backend.py` is the one table the docs and error messages read, and `describe_backend` names the resolved endpoint at the step-7 gate so the user can see which host is about to receive their rubric. `ORQ_API_BASE_URL` now also moves every control-plane call (`lib/orq_client.py` had the API host hardcoded with no override at all, so a custom host could be set for the router and the deployment backend but not for reading evaluators, traces, projects or datasets). API keys stay environment-only by design — a `--backend_api_key` flag would put a live credential in shell history and in every `ps` listing — and a missing key names the variable it wanted.
- `orq-evaluator-alignment`: a narrow escape hatch to the "never read the raw artifacts" rule. Reading a **single** datapoint by `source_index` is now sanctioned when the payload lacks a field the decision needs; the blanket prohibition was pushing the conductor toward guessing instead.
- `orq-evaluator-alignment`: a step 0 that asks whether the user actually has a judge in orq before anything else runs. Three routes: an evaluator id continues into the flow; a bare prompt is set up as an evaluator first (via `orq-build-evaluator`) and then continues; neither hands off to `orq-build-evaluator` and stops. Previously the flow opened by demanding an id, which is the one thing a user who needs this skill most may not have.
- `orq-evaluator-alignment`: `grey_zone.py assemble --include_low_flip` to opt the stable spot-check rows back into the payload, and `n_low_flip_excluded` / `n_confusers` in the `budget` block so the conductor can state what actually entered context.
- `orq-evaluator-alignment`: **the retest reports a `before` for signal (b), and the caveats that make both signals softer than they look.** Agreement previously had no baseline, so "accuracy 0.78, PASS" read as a win even when the original judge had scored 0.85 on the same labels — and that number costs nothing, because the original run already judged those very rows. `retest_metrics.json` now carries `agreement.before` alongside a `caveats` list the conductor is told to read out: the retested rows were selected for maximum observed instability (so re-measuring them regresses toward the mean on its own), the same examples produced the rewrite guidance *and* the labels scoring it (no holdout in v1), and any label the user did not confirm is the conductor's application of their rule rather than their verdict.
- `orq-evaluator-alignment`: `retest.py --baseline_rerun` re-runs the **original** judge over the same rows in the same pass. It doubles the cost and is the only version of gate (a) that isolates the rewrite from the selection effect; off by default, offered rather than assumed.
- `orq-evaluator-alignment`: `retest.py --with_low_flip` re-judges the queue's stable spot-check rows as an unlabelled regression check, reporting how many changed verdict. The step-5 promise to spot-check the rows the judge was completely sure about was never kept on the default path — they were excluded from the payload and, being unlabelled, from the retest too — so a rewrite that settled the grey zone by unsettling everything else was invisible. SKILL.md step 6 now also has the conductor read those rows with the user before the rewrite.
- `orq-evaluator-alignment`: `grey_zone_policy.json` labels carry a `label_source` (`derived` | `human_confirmed`) and SKILL.md gates on reading the derived labels back to the user. The human answers a *rule* question and the conductor derives each point's value from it, so by default the ground truth the retest scores against is model-derived; `apply` warns with the counts and `retest_metrics.json` records them, rather than presenting one model's reading of the rule as a human verdict.
- `orq-evaluator-alignment`: `validate_policy` checks every label against the evaluator's own verdict space. SKILL.md says never invent a label or move the scale and nothing enforced it, so an invented categorical label or an out-of-scale score passed validation, entered the rewrite guidance, and then scored 0 accuracy at step 8 — which reads as a judge failure rather than the policy error it is. Numeric tolerances must also be non-negative numbers, and a label may not reference a grey zone the policy never declares.
- `orq-evaluator-alignment`: `stability.json` and `queue.json` record a `traces_fingerprint` of the `traces.jsonl` their `source_index` values point into (`lib/content.traces_fingerprint`, sharing the scanner's own row-identity key). The grey-zone assemble warns on a mismatch and `retest.py` refuses outright.

### Removed
- `orq-evaluator-alignment`: `scripts/run_experiment.py`, superseded by `retest.py` since the Part 2 feedback loop and left behind rather than kept. It was not merely unused — it was **wrong** on the skill as it now stands. It selected labelled rows with `isinstance(value, bool)`, so on a categorical or numeric judge it silently scored **zero** rows; it hard-required `annotations.json`, which is the UI *fallback* artifact rather than the default `grey_zone_policy.json`; and it checked agreement alone, when the whole premise since Part 2 is that agreement without an instability drop is gameable. `retest.py` covers every case it did, for all types, on both signals. The one thing genuinely lost is `--recommend_only`, its variance-aware suggestion for the retest repeat count — that logic was boolean-only (it keyed off `flip_rate`) and `SKILL.md` already replaced it with an explicit instruction to use at least the stability run's N. Its two orphaned config keys (`retest_repeats`, `retest_repeats_cap`) go with it; the retest reads `n_repeats`.

### Changed
- `orq-evaluator-alignment`: the skill's `README.md` and the repo-level surfaces (root `README.md`, `agents/AGENTS.md`, `tests/skills.md`) describe what the skill now is. All three still advertised a **binary Pass/Fail** judge and a per-row annotation queue — the pre-RES-978 shape — so the skill's own docs were the last thing claiming it couldn't do categorical or numeric, and the smoke tests were verifying the flow it no longer runs. The skill README's pipeline table had also drifted past four new scripts and named a default backend that is no longer the default. The `SKILL.md` description now names the question-led grey-zone flow, which is the trigger a user most plausibly types ("my judge keeps changing its mind").
- `orq-evaluator-alignment`: `lib/seed.py` reads the shared `lib/content.field_for_variable` table instead of keeping a hand-mirrored copy of the suffix rules. That copy is what produced the 2.4.1 bug where a `{{log.reference}}` evaluator had every seeded row silently skipped; there is now one table and no mirrors, pinned by a test asserting every judge-fillable leaf resolves.
- `orq-evaluator-alignment`: the grey-zone payload renders a conversation through the same parts-aware helper the judge renders with, rather than dumping raw JSON. On a Responses-API row the text sits under `parts[]`, so the dump spent the character budget on structural noise and showed the conductor a different artifact than the judge was given.
- `orq-evaluator-alignment`: the recovery menu moved from step 4a to **step 1a** and is now offered the moment the trace scan comes up short, not several steps later after the user has already committed to a run. It gained a fourth option — bring your own examples from outside orq — alongside looking further back, using an existing orq dataset, and generating cases; the second-model option is now scoped to the flat-profile case it actually addresses.
- `orq-evaluator-alignment`: `config.toml`'s section comments use the same step numbers as `SKILL.md`. They still numbered the recommendation and rewrite as steps 8 and 9 from an earlier draft of the flow, which is the sort of drift that sends a reader looking for a step that no longer exists.
- `orq-evaluator-alignment`: `fetch_traces` takes its dedup key from `lib/content.judged_input_key` rather than keeping a private copy, so the definition of "the same datapoint" is shared with the fingerprint guard by construction.
- `orq-evaluator-alignment`: SKILL.md rewritten for a non-specialist reader. The conductor now describes judge behaviour ("it gave a different answer 6 times out of 8") rather than the statistics that measured it, and the internal vocabulary — confuser, grey zone, instability band, open-code, conductor — is kept out of what it says to the user. Each step opens with a sentence on what is about to happen and why.

### Fixed
- `orq-evaluator-alignment`: **numeric instability could not reach 1.0**, so the three output types were not on one scale despite everything downstream reading them as if they were. `numeric` divided the population standard deviation by the full declared scale range, but a maximal split — half the repeats at each end of the scale — has a standard deviation of exactly half the range, so the most unstable numeric judge possible scored 0.5, where boolean and categorical both reach 1.0. The denominator is now half the range, so 1.0 means "as split as this judge can be" for every type. Existing numeric scores double: the worked example (population stdev 1.5 on a 1–10 scale) moves from 0.17 to 0.33, and rows that sat just under a band edge move up one band. The bands themselves (`<0.1` stable, `0.1–0.3` noisy, `>0.3` unreliable) are unchanged, so a numeric run recorded before this release cannot be compared band-for-band against one recorded after it.
- `orq-evaluator-alignment`: **`serve_annotation.py` could not start.** Its PEP 723 block declared only `fire` while the module imports `loguru`, and `uv run` builds the script's environment from that block and nothing else — so the documented command in `SKILL.md` died with `ModuleNotFoundError` before serving a single page. This is the fallback the grey-zone flow falls back *to*, for the case where the confusers don't cluster, which is exactly when nobody has a second option. The rest of the suite could never catch it, because pytest runs with every dependency installed; `tests/test_script_deps.py` now parses each step script's inline metadata and its imports and compares them, so the declared set is verified in the environment that actually matters.
- `orq-evaluator-alignment`: **the numeric agreement band ignored the scale it was measuring**, which is the reverse of the argument that makes instability normalize by the declared range. `numeric_agreement` compared against an absolute `tol` defaulting to 0.5, so the gate read differently on every judge: a rewrite disagreeing with the human by 40% of a 0–1 groundedness scale **passed**, while one within a single point everywhere on a 0–100 scale **failed**. Since signal (b) exists precisely so signal (a) can't be gamed, having it go vacuous on the 0–1 scale most groundedness judges use defeats the point. The band is now derived from the evaluator's declared scale (`lib.agreement.default_tolerance`, 10% of the range by default), with an absolute override still available.
- `orq-evaluator-alignment`: **one config key for the numeric band, not two.** `recommend.py` read `numeric_tolerance` while `retest.py` and `cross_model.py` read `numeric_tol`, and neither appeared in `config.toml` — so setting the one that looked right moved what counted as a disagreement in one step and left the gate that signs the rewrite off sitting on its default. `numeric_tol` is now the single key, read by all three, and it is documented alongside `numeric_tol_fraction` and the four `retest_min_*` gates that were also read from `cfg` and named nowhere.
- `orq-evaluator-alignment`: **the human's per-point numeric tolerances stopped being thrown away.** `validate_policy` requires a `tolerance` on every numeric label and `policy_labels` carries it through, but the retest honoured it only when every point happened to share one band — otherwise several considered bands from the human were silently replaced by the configured default, and `_pair_with_labels` never read the field at all. `numeric_agreement` now takes per-pair bands and reports `tol_source`.
- `orq-evaluator-alignment`: **gate (a) could be passed by rows going *unmeasurable*.** The "before" mean was carefully recomputed over the retested rows, but the "after" was the retest run's own `mean_instability` — an average over whatever that run could measure. A rewrite that answers off-contract on more than half a row's repetitions drops that row below `metrics.py`'s floor, out of the retest average, and the remaining rows average lower; the rows selected for a retest are the most unstable in the run, so that is precisely where it would happen. Both means are now taken over the rows *both* judges could measure, with `n_rows_compared`, `n_lost_unmeasurable` and the retest's off-contract count in `retest_metrics.json`, a warning when any row is lost, and a caveat naming the failure mode.
- `orq-evaluator-alignment`: `parse_numeric` accepts a quoted number in the schema (`{"value": "4"}`). Models quote numbers routinely; requiring a bare int/float sent those completions down the free-text path, where the surrounding explanation's own digits made the verdict line ambiguous and a judge that had answered correctly in the schema it was handed was recorded as off-contract.
- `orq-evaluator-alignment`: the instability report names the rows with off-contract repetitions, not just the dataset-wide total. A row can answer off-contract half the time and still band as `stable` on the rest, and the aggregate count could not say which row that was — which is the row a reader is about to trust.

- `orq-evaluator-alignment`: the grey-zone payload no longer silently overrides the count the user chose. `build_queue` appends `low_flip_sample_size` (default 5) *stable* spot-check rows to the queue, and `assemble_payload` was taking the whole queue — so "review 3 with me" put 3 + 5 = 8 examples into context, five of which had no grey zone in them by construction. Those rows are a control group for annotation, not material to open-code; they are excluded by default and reported separately.
- `orq-evaluator-alignment`: the aligned copy is named after its source instead of after an opaque id. `GET /v2/evaluators/{id}` returns an empty `key` for evaluators created through the current orq UI, so the old fallback produced keys like `01kzxt86ac82d1fvzw3s8wfv83-aligned-<ts>`. The name is now resolved `key` → `display_name` → `raw.key` → id, giving `groundedness-bool-testcase-aligned-<ts>`. The key is what matters here: orq overwrites the `display_name` sent on create with the key, verified against the live API.

The evaluator record carries no `path` on either the detail or the list endpoint, so the source's folder cannot be read back directly; the new `resolve_project_key` maps the id it *does* carry to the project key that heads a create `path`. Both spellings are read, the project record is matched on any of its id fields, and the lookup pages through `/v2/projects` instead of reading only the first page. Falls back to the workspace root when the project can't be resolved, instead of inventing a folder.
- `orq-evaluator-alignment`: **a free-text numeric judge no longer gets the wrong score, silently.** `parse_numeric` fell back to the *first* numeric token in the completion, so `'On a scale of 1 to 5, I give this a 4'` parsed as **1.0** with status `ok` — inside the declared scale, so nothing downstream re-checked it, and the wrong score entered `mean`, `stdev` and the instability band. It now reads the verdict the way `parse_categorical` does (after the last `Value:`/`Score:` label, else the last line), scrubs scale mentions (`of 1`, `to 5`, `out of 5`, `/5`) first, and surfaces a verdict line still carrying two different candidates as `wrong_output_type` rather than guessing between them.
- `orq-evaluator-alignment`: the preservation guard no longer passes a moved verdict space on a substring match. `endpoint not in proposed` is True for a rubric that only ever says `10`, so a rewrite moving the scale from `[1, 5]` to `[1, 10]` cleared the gate while both endpoints were in fact gone; the same shape let a dropped `spam` label read as preserved by a rubric mentioning `spammy`. Both are matched on their own boundaries now.
- `orq-evaluator-alignment`: real judge reasoning is no longer discarded as a jury placeholder. `_is_real_rationale` substring-matched `not available` / `no explanation`, so `'the tool was not available at inference time, so the claim is ungrounded'` was classed as no-rationale and the conductor was told there was nothing to read when there was. The generic phrases now only count as placeholders when they are the whole rationale; the distinctive jury notice still matches anywhere.
- `orq-evaluator-alignment`: `retest.py --num_samples` broke the comparison it was meant to smoke-test. The label scope stayed the full set while `num_samples` narrowed only the retest stability run, so `original_mean` covered every labelled row and `retest_mean` covered the first few — the subset-vs-full-run artifact the surrounding code exists to avoid. It now caps the selection itself, so both sides cover the same rows.
- `orq-evaluator-alignment`: the retest defaults its repeat count and temperature to whatever the original stability run actually used, read back from `metrics.json`, instead of to the config. Instability is estimated from N samples at a temperature and both bias the estimate, so retesting at different ones compared two different measurements; temperature was not forwarded to the retest run at all. A deliberate override to *fewer* repeats now marks the comparison not comparable rather than letting the sample size read as an improvement.
- `orq-evaluator-alignment`: label loading no longer discards half the labelling. `retest`/`rewrite` preferred `grey_zone_policy.json` whenever it existed, but the documented fallback runs in the other direction — try the grey-zone Q&A, find the examples don't group, open the annotation UI — so the labels collected last were silently ignored. Both files are now merged into one label set keyed by `source_index`, with the annotation winning a datapoint both cover. Merging rather than picking also removes a file-mtime dependency: the same run directory now scores the same way twice.
- `orq-evaluator-alignment`: the numeric `scale` is no longer sent on create. The evaluator schema has no scale field and the API drops it, so the request only looked like it carried a guarantee it never had; a numeric judge's scale lives in its rubric text, which the preservation guard is what actually protects.
- `orq-evaluator-alignment`: the grey-zone payload honours `max_chars` for real. The elision marker and the `name: ` prefixes were added on top of the budget, so a 600-char ceiling across several variables rendered close to a thousand; both are charged against it now, and a budget too small to give every variable a character resolves to zero rather than overspending.
- `orq-evaluator-alignment`: cross-model disagreers are labelled and counted in the payload. The queue appends them after the instability ranking, so the token clamp drops them first — and on a judge that never wavers they are the entire signal. Each confuser carries its `reason`, and the budget block reports `n_dropped_cross_model`.
- `orq-evaluator-alignment`: `testcases/rag-groundedness/answer_key.json` no longer contradicts itself. `G3c` was listed both as unstable at 0.5 and as a stable-but-wrong case on the same judge; it is wrong *and* unstable, which is a different thing, and now sits in its own `unstable_and_wrong_cases`. `PC3` claimed six stable-wrong cases and named seven ids, three of which (`T1`, `T2`, `T4`) appear in neither measured baseline and are not accounted for by either run's agreement count — it now states what was measured and flags the traps as designed-but-unconfirmed.
- `orq-evaluator-alignment`: **the grey-zone payload no longer silently omits most of the judged input.** When judge-template inversion failed, `_compact_input` fell back to `output or query` — and on a row captured in the structured Responses-API shape `output` is the assistant's *answer*, not the rendered prompt. So a groundedness judge's context and question, the only things groundedness can be checked against, never reached the conductor. Ties are where seeing both sides matters most and are exactly where no rationale exists, so the payload now carries `reasoning_available` / `n_no_rationale` and the conductor states the gap. - `orq-evaluator-alignment`: `retest.py` re-judged **every** row in `traces.jsonl` rather than the labelled ones, despite `_build_retest_dir`'s docstring claiming otherwise — a 24-row run with 8 labels cost 24 × N calls, triple what the skill quoted, while agreement still scored only the 8. - `orq-evaluator-alignment`: **`metrics.py`'s correctness block stops computing numbers that look like a measurement and aren't.** Three cases used to score a comparison that was never meaningful: an evaluator that declares a reference-family variable (`{{log.reference}}`, `{{expected}}`, `{{expected_output}}`) was shown `reference` as judge INPUT via `lib.judge.make_replacements`, so grading its verdict against that same value was circular, not a check — the new `lib.content.reference_is_judge_input` rule short-circuits it, returning `n_labelled: 0` and a `reason_omitted` instead of a number; a categorical `reference` outside the judge's own declared label set was compared anyway, scoring a vocabulary mismatch as the judge being wrong, and is now excluded and counted in `n_unreadable_labels`; and numeric with no declared scale and no configured `numeric_tol` used a fixed absolute band that meant nothing on that judge's scale, and is now omitted with the same `reason_omitted` shape rather than computed against an arbitrary number. `by_band.stable`'s headline claim is gated the same way: it only earns "the consistently-wrong blind spot, measured" once the labelled subset covers at least 10 rows and at least 90% of the stable band — below that floor the report captions it "partial view — do not conclude 'consistent-and-right' from this" instead of the stronger claim the coverage doesn't support yet.

- `orq-evaluator-alignment`: **the confuser queue's `--count` now caps what it actually promises to cap, and never double-counts a row.** `build_queue.py` gained a third confuser class, `wrong_vs_reference`, in the previous release, but `--count` only capped the flipped/cross-model classes — a large wrong-vs-reference tail could slip past a user-chosen count uncapped. `--count` now caps the COMBINED confuser list (flipped, then cross-model, then wrong-vs-reference — the cap trims the tail), `queue.json`'s `meta` gains `n_wrong_vs_reference` alongside the existing counts, the low-flip sanity sample never re-offers a row already queued under another reason, and each item carries `judge_correct` so the conductor can group by *how* the judge is wrong rather than only by what it is unsure about.
- `orq-evaluator-alignment`: **four smaller honesty gaps at the pipeline's edges.** `scan_truncated` was computed from the date-window-filtered trace count, so a tight `trace_start_date`/`trace_end_date` could hold few rows while the raw scan still hit `trace_limit` — the note then told the user a deeper scan couldn't help when it, in fact, could; it now reads the raw pre-window fetch depth. `--map` onto the reference field used to be silently overwritten by the `expected_output` derivation running after it, and an unmappable `--map` variable leaf (a typo like `log.outout`) parsed successfully and then no-op'd forever; `--map` onto `reference` now wins, and an unmappable leaf is a `ValueError` naming it, at parse time. `create_eval.py` gated creation on `var_check_passed` alone, so a rewrite whose verdict space had shifted — a dropped categorical label, a moved numeric scale — still created cleanly as long as the `{{...}}` variable set matched; it now enforces `verdict_space_ok`/`preservation_ok` too, `--force` bypasses all three, and `approval.json` records which were forced in `forced_checks`. And `rewrite_eval.py` now warns when `grey_zone_policy.json`/`annotations.json` were touched after `aggregated.md` was last written — the summary the rewrite is about to act on would otherwise silently predate the latest human input.
- `orq-evaluator-alignment`: **a numeric retest with no way to size gate (b)'s tolerance now refuses before any judging, instead of silently scoring against an arbitrary band.** `_resolve_numeric_tol` bottomed out at `lib.agreement.FALLBACK_TOL` (0.5) when there was no `--tol`, no uniform grey-zone policy band, no configured `numeric_tol`, and no declared scale — the exact situation `metrics.py::_correctness` already refuses on (`reason_omitted`), but the retest gate went ahead and scored against it anyway, silently making gate (b) vacuous on the 0–1 judges most groundedness rubrics use. `_resolve_numeric_tol` now also returns which of `cli`/`policy_uniform`/`configured`/`scale_derived`/`fallback` produced the band, so `main` can refuse on the `fallback` case specifically — before the retest sub-run is materialized or judged — naming the remedies (`--tol`, `numeric_tol` in `config.toml`, a declared scale via `fetch_evaluator.py --scale_min/--scale_max`, or per-point grey-zone bands). The `--tol` resolution chain documented in `SKILL.md`/`config.toml` no longer claims it ends at an absolute 0.5 for the retest specifically (`cross_model.py`'s own probe is unchanged and still falls back to it).
- `orq-evaluator-alignment`: **`selection_bias_controlled` now reports what the run actually did, not which flag was passed.** It was set from `bool(baseline_rerun)`, so a `--baseline_rerun` that found no rows measurable on both sides (`baseline_mean is None`, falling back to the original-run comparison a few lines later) still claimed `true` — the one field that exists to say whether THIS run isolated the rewrite from the selection effect was, in that case, wrong. Set from the outcome (`baseline_mean is not None`) instead, matching the caveat logic that already keyed off the same condition.
